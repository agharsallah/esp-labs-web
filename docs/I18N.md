# Languages (i18n)

The guide speaks English (the source), French, Spanish, Italian, German, Polish, Turkish, Simplified Chinese, Traditional Chinese, Japanese and Arabic (right to left). Interface text goes through [i18next](https://www.i18next.com/) and [react-i18next](https://react.i18next.com/); long-form content (lessons, the phrasebook, code tours) is translated as JSON overlays on the TypeScript source. This page is the contract for every change that adds or moves text.

## Layout

```text
src/i18n/                     the machinery (no app text in here)
  locales.ts                  LOCALES, LOCALE_INFO (native name, BCP 47 tag, direction), matchLocale
  namespaces.ts               interface namespaces: CORE (loaded up front) and LAB (loaded with the widgets)
  i18n.ts                     the i18next instance: lazy JSON chunks, <html lang dir>, follows the picker
  locale-store.ts             the reader's choice ("auto" or a language), per browser
  use-locale.ts               useLocale() / useLocaleInfo() for components
  overlay.ts                  extract / apply / check content overlays (pure, tested)
  catalogue-check.ts          checks an interface catalogue against English (plurals, markup, placeholders)
  i18next.d.ts                types t() keys from the English catalogues: a wrong key fails the build
src/content/text-policies.ts  which content fields are text (everything else is structure)
src/content/localize.ts       loads a content overlay and lays it over the source
src/locales/<locale>/
  <namespace>.json            interface text, one file per namespace
  content/lessons/<track>.json, content/glossary.json, content/tours.json   content overlays
```

English interface catalogues (`src/locales/en/*.json`) are written by hand: they are the source. English content catalogues (`src/locales/en/content/**`) are **generated** from the TypeScript content by `pnpm i18n:extract`; `src/content/catalogues.test.ts` fails while they are stale. Translators (people or agents) only ever edit `src/locales/<locale>/`.

## Which language is shown

In order: the URL's `?lang=` (`#/lessons/02?lang=ar`, or `?lang=ar` before the hash), then the reader's saved choice (Settings or the footer picker), then the first supported language in `navigator.languages` ("Follow my browser", the default), then English. A URL that names a language also becomes the saved choice. Every URL carries the language on screen (`app/locale-url.ts` adds it after each navigation, replacing the history entry), so any link a reader copies opens in their language.

## Interface text

```tsx
const { t } = useTranslation("home");          // the feature's namespace
<h2>{t("continue.title")}</h2>                  // nested keys, grouped by component
<p>{t("tracks.done", { count })}</p>             // plurals: tracks.done_one / tracks.done_other in English
<button aria-label={t("player.next")}>          // aria-label, title, alt and placeholder too
<Trans t={t} i18nKey="layout.brand" components={{ part: <span className={styles.part} /> }} />
<RichText text={t("hint.tap")} />               // for <b>, <i>, <code> inside a sentence
```

- **One namespace per feature**: `common` (shell, shared `ui/`), `home`, `lesson`, `code`, `settings`, `bench`, `parts`, and `labs-<track>` / `labs-shared` for the simulators. Core namespaces load before the first paint; a lab namespace loads when its widget does (react-i18next suspends inside the widget's `Suspense`).
- **Keys** are camelCase, nested by component then purpose (`stepper.trace.label`), never the English text itself.
- **Always pass `t` to `<Trans>`.** The React Compiler memoizes elements whose props did not change; without `t={t}` a `<Trans>` keeps the previous language after a switch.
- **Whole sentences only.** Never concatenate translated fragments or build sentences with `+`: word order differs (German verbs at the end, Japanese particles, Arabic right to left). Use `{{placeholders}}`, and `<Trans>` with named components (`<link>…</link>`) when part of a sentence is a link or a styled span.
- **Plurals** always go through `count`: English has `_one` and `_other`; Arabic needs `_zero`, `_one`, `_two`, `_few`, `_many`, `_other`; Chinese and Japanese only `_other`. The catalogue test enforces each language's CLDR forms.
- **Numbers, dates and units** go through `Intl` with the locale's tag (`useLocaleInfo().tag`), or i18next's built-in formatters (`{{value, number}}`, `{{at, datetime}}`). Never `toFixed()` into a sentence.
- **Pure modules stay pure.** `domain/` and simulator logic never import the i18n instance: they return ids or keys (`{ key: "beginner" }`), or take a `t: TFunction` argument when they compose sentences (the code explainer does). Components translate.
- **Data tables of labels** (levels, views, choices) keep only their keys in TypeScript; the labels live in the catalogue (`t(\`levels.${level}.label\`)`). Template-literal keys are type-checked against the catalogue.

`pnpm lint` enforces this: `i18next/no-literal-string` fails on words written straight into JSX (symbols, all-caps silkscreen labels and numbers with units are allowed). A file whose literal text is deliberately English (a firmware page, host names, key names) says so in a file-level `eslint-disable` comment with the reason.

### What stays in English

- Code, commands, file paths, pin names (`GPIO 4`, `3V3`), C++ words, library and API names, units (`ms`, `MHz`).
- **What the hardware itself prints or draws**: serial monitor lines from the firmware, text on the simulated TFT screen, the BLE advertising names. The simulators show what the real board shows, and the real firmware is in English. Captions, buttons, legends and explanations *around* a simulator are interface text and are translated, including labels drawn on canvas diagrams (pass the translated string into the draw function).
- Log messages (`createLogger`), test ids, storage keys, URLs.

## Long-form content

Lessons, the phrasebook and the tours stay authored in TypeScript (`src/content/`), English only. Their text is pulled out into catalogues by a **text policy** (`src/content/text-policies.ts`): a list of field names whose values are reader-facing text (`goal`, `steps`, `does`, `say`…). Everything else — ids, pins, commands, widget ids, code anchors, `status` (machine-read by `domain/progress`) — is structure: it never reaches a translator and is never read from a translation.

A translation is an overlay with the same tree: array items are keyed by `id` / `key` / `env` / `path`, else by index. At load time (`trackLessonsQuery(track, locale)`, `codeContentQuery(locale)`) the overlay is laid over the source; any text it lacks, or gives in a different shape (a step added since translation), shows in English. So a partial translation is always safe to ship.

After editing content: `pnpm i18n:extract`, then translate the changed keys in each language.

## Right to left, and scripts with their own rules

`<html lang dir>` follows the language (`i18n.ts`), so the browser, CSS `:lang()` and `[dir="rtl"]` do the work:

- **Logical CSS only**: `margin-inline-start`, `padding-inline`, `inset-inline-end`, `border-inline-start`, `text-align: start`. Never `left` / `right` except to centre something (`left: 50%` + `translateX(-50%)`). Sideways motion multiplies by the direction sign: `translateX(calc(4px * var(--dir)))`.
- **Things that do not mirror** carry `dir="ltr"`: code views, the serial terminal, commands, the board pinout (the board has a physical left and right), canvases and 3D scenes. `code`, `kbd`, `pre` and `samp` are LTR and bidi-isolated globally, so a snippet inside an Arabic sentence keeps its order.
- **Directional icons** (`arrow`, `back`) mirror automatically (`Icon` marks them `data-directional`). Add new "next/previous" icons to `DIRECTIONAL`.
- **Scroll positions** in an RTL scroller are negative: measure with `getBoundingClientRect()` relative to the scroller, or use `scrollIntoView({ inline: "center" })`, instead of `scrollTo({ left })`.
- **Arabic**: no letter-spacing (it breaks the joined letters), no italic (emphasis becomes weight), taller leading (`--leading`). **Chinese and Japanese**: no letter-spacing, strict line breaking, taller leading; Japanese wraps at phrase boundaries (`word-break: auto-phrase`). `text-transform: uppercase` does nothing in these scripts, so never rely on case alone for meaning.
- **Fonts**: Archivo and IBM Plex Mono have no CJK or Arabic glyphs; `tokens.css` adds each script's system font (`--font-script`) after them, so nothing extra downloads.
- **Length**: German and French run ~30% longer than English, Chinese and Japanese much shorter. Let labels wrap, avoid fixed widths on text, and check the 390 px layout in German.

## Adding a language

1. Add its code to `LOCALES` and its `LOCALE_INFO` (native name, BCP 47 tag, `dir`).
2. Create `src/locales/<code>/`: one JSON file per namespace and the content overlays, mirroring `src/locales/en/`. Any file may be partial; missing text falls back to English.
3. If its script needs it, add a `:root:lang(<code>)` block to `tokens.css` (fonts, leading) and any typographic rules to `base.css`.
4. `pnpm check`: the catalogue tests reject unknown keys, wrong plural forms, and changed markup or placeholders.

## Translation style

The guide talks to a curious beginner: short sentences, plain words, second person, warm but not chatty. Translations keep that voice in the target language (informal `tu`/`du`/`tú` in French, German, Spanish and Italian, informal `ty` in Polish, informal `sen` in Turkish; polite plain form in Japanese, です/ます; Modern Standard Arabic; Simplified Chinese and Traditional Chinese with a neutral, friendly tone; Traditional uses Taiwan wording). Technical words that learners will meet in tools and datasheets (GPIO, PWM, SPI, serial monitor in Japanese as シリアルモニタ, …) follow the established usage in each language's maker community.
